# zipcodetw-js

Find a Taiwan ZIP code by address, fuzzily and gradually — a dependency-free
JS port of [moskytw/zipcodetw](https://github.com/moskytw/zipcodetw)'s
matching algorithm. Runs entirely client-side: no server, no WASM, no SQLite.

```js
import { find } from 'zipcodetw-js';

find('臺北市信義區市府路1號'); // '110204'
find('臺北市信義區');          // '110'  (partial address -> partial code)
find('臺北市');                // '1'
find('松山區');                // '105'  (road/district name alone, no city)
find('台北市秀山街');          // '100005' ("台" normalized to "臺")
```

For the browser, fetch the two data files yourself and construct a
`Directory` directly (no filesystem access, so `src/node.mjs` doesn't apply):

```js
import { Directory } from 'zipcodetw-js/browser';

const [gradualTsv, preciseTsv] = await Promise.all([
  fetch('/data/gradual.tsv').then(r => r.text()),
  fetch('/data/precise.tsv').then(r => r.text()),
]);
const dir = new Directory({ gradualTsv, preciseTsv });
dir.find('臺北市信義區市府路1號'); // '110204'
```

## Why this exists

The original `zipcodetw` builds a SQLite index at install time and queries
it from Python. The query logic itself (tokenize an address, normalize
Chinese numerals/width, match house-number-range rules like 單/雙/以上/以下/至)
has no SQL in it — it's plain string/regex work. This port keeps that logic
and replaces the SQLite index with a flat, front-coded TSV bundle that loads
straight into two `Map`s.

Measured on the bundled 2102_01 (2021-02) dataset — 77,721 precise rules +
161,516 gradual entries, the whole of Taiwan:

| | |
|---|---|
| Transfer size | **0.77 MB** (brotli) / 1.18 MB (gzip) |
| Index build (parse bundle) | ~60 ms |
| Memory after load | 12–70 MB depending on data structure (Map-based vs packed-string + binary search) |
| Per-lookup | ~4–6 µs |
| Correctness | **100% match** against the Python reference over 88,271 differential test queries (see `test/`) |

## Correctness gotchas found while porting

These are the things that silently produce wrong answers if you're not
careful translating this algorithm to JS:

- **Rule order is an implicit dependency.** `find()` returns the *first*
  matching rule for an address. Python's `Directory.find()` reads rules via
  the `(addr_str, rule_str)` SQLite index, so it sees them in `rule_str`
  order — not insertion order. Exporting the bundle without
  `order by addr_str, rule_str` produced 483 silently-wrong 6-digit codes
  out of ~88k test queries (all valid-looking codes — no error, no crash).
- **Operator precedence differs.** Python's `x & 1 == 1` is `(x & 1) == 1`;
  the equivalent in JS (`x & (1 === 1)`) is nonsense — the odd/even rule
  needs explicit parens.
- **`Address.flat(i)` slices the *front*, not from `i`** — it maps to
  Python's `tokens[slice(i)]`, i.e. the first `i` tokens.
- **`re.findall` yields `''` for unmatched groups; `matchAll` yields
  `undefined`.** Token equality checks need `?? ''` or they silently never
  match.
- **`'' in '村里'` is `True` in Python** — relied on by the village/neighborhood
  fallback branch. `'村里'.includes(unit)` in JS happens to agree (empty
  string is a substring of everything), but it's worth knowing that's not
  a coincidence you want to lean on elsewhere.
- Tuple comparison (`(no, subno) >= (no, subno)`) needs an explicit
  comparator in JS; there's no tuple `>=`.

All of the above is exercised by `test/zipcodetw.test.js`, which replays
88,271 real queries (stride-sampled across the full dataset, generated by
`scripts/`-adjacent tooling against the actual Python package) and asserts
byte-for-byte agreement.

## Comparison to existing npm packages

Checked before starting this port — nothing on npm does free-text fuzzy
address parsing:

| Package | What it actually takes as input |
|---|---|
| `jquery-twzipcode` / `react-twzipcode` / `vue-twzipcode` / `zipcode-tw-react` | Structured city/district *selection* (dropdown-style UI components) |
| `@simoko/tw-zip` | **Structured fields** — `{ city, area, road, number, lane, alley }`. It *does* correctly resolve odd/even and above/below/between house-number ranges (verified against known cases), and ships smart per-city lazy-loaded data (1.4 MB uncompressed total). But it requires the caller to have already split the address into fields — it has no tokenizer and cannot take a raw string like `"臺北市信義區市府路1號"` or a partial/misordered address. |
| `zipcode-taiwan`, `twzipcode-data` | Static city/district → 3-digit code tables only |
| `zipcodetw` (Python, this port's source) | Free-text fuzzy/gradual parsing — the actual target being ported |

If your inputs are already structured form fields, `@simoko/tw-zip` is a
solid, actively maintained choice and probably less work than adopting this.
This port exists for the case where you have a raw address string (user
paste, OCR, an existing text field) and need to resolve it without a backend
round-trip.

## Data

`data/2102_01.csv` is Chunghwa Post's (中華郵政) postal directory, vintage
2021-02, vendored from the upstream Python project — **the upstream repo has
not been updated since 2022-04**, so this is stale by several years' worth of
new roads/developments. Regenerate `data/gradual.tsv` and `data/precise.tsv`
from a fresher CSV with:

```bash
pip install zipcodetw   # build-time only; not a runtime dependency
npm run build            # data/2102_01.csv -> data/gradual.tsv, data/precise.tsv
```

Verify the data's usage terms before commercial deployment.

## Status

Early scaffold. The core algorithm (`src/zipcodetw.mjs`) is differentially
tested and correct. Not yet published; no bundler/minification setup, no
browser demo page, no automated data-refresh pipeline.
